## Implementation

### Transition model and idempotency

Added operation ledger records under `system/role_operations/operations/{operationId}` and transition fields on the target profile: `operationId`, backend-generated `transitionId`, `transitionStartedAt`, `transitionAttemptCount`, `pendingRole`, `pendingIsActive`, `pendingRoleVersion`, `roleVersion`, `roleTransitionStatus`, `provisioningStatus`, and `claimsOutOfSync`.

`beginRoleTransition` generates a new transition ID inside the trusted Functions process and commits the operation record, pending profile intent, and any Admin counter delta in one Firestore transaction. A retry with the same operation ID and target resumes the same transition; it does not apply the counter delta or roleVersion increment again. Reusing an operation ID for another UID or a different desired role/status fails. A second operation against a pending target fails. Completed operations are checked against the current profile before being reported as idempotent success.

The operation ID is an idempotency key accepted from the caller when supplied; if omitted, the backend creates one and returns it on success or in post-commit error details. `transitionId` is always generated by the backend. Firestore Rules deny client writes to every new profile field and to the operation ledger, including its subcollection.

### Shared claims helper

Added `setRoleClaims` as the sole code path that calls `setCustomUserClaims`. It reads existing claims, preserves unrelated keys, and updates `role`, `isActive`, `roleVersion`, and `lastUpdated`. Role transitions, Technician provisioning, student profile trigger handling, and the seed script all route through this helper, directly or through the shared transition finalizer.

### CAS finalization

`applyRoleTransition` validates that the operation record and profile agree on UID, operation ID, transition ID, desired role/status, and pending version. It applies Auth claims and disabled state, then finalizes profile and operation records in one Firestore transaction. The transaction clears pending fields only if the same operation and transition remain pending at the expected version; it does not touch the Admin counter.

Concurrent finalizers for the same intent are idempotent. An old finalizer cannot complete a later transition. The emulator suite initially exposed a race where a second finalizer failed after the first had already completed; the retry path was corrected to recognize the exact completed operation. The full emulator suite passed after that correction.

### Token validation and legacy compatibility

`requireFreshToken` now compares token role, active state, and roleVersion with the completed profile and rejects invalid versions, pending/failed provisioning, pending transitions, or Claims mismatch.

Migration policy: an existing profile with no `provisioningStatus` or `roleTransitionStatus`, no out-of-sync flag, a boolean active state, and absent/1 `roleVersion` is treated as legacy version 1. A token without `roleVersion` is accepted only against profile version 1 and only when all other role/profile checks pass. Invalid version values fail closed. The first role transition upgrades the profile and token to version 2; after that, a missing or stale token version is rejected. No bulk profile migration was run.

All five privileged callable exports call `requireFreshToken(request)` before processing, then apply Admin authorization where required:

- `createTechnician`
- `updateUserRole`
- `reconcileRoleTransition`
- `deactivateUser`
- `reactivateUser`

### Seed and provisioning compatibility

The seed script now resumes the operation ID/transition ID already stored in a pending target, writes the operation record in the same control/profile transaction, and completes via the shared finalizer. It uses the shared compiled helper, so run `npm --prefix functions run build` before running seed. It was **not** run in this task. The existing Technician lifecycle was not redesigned; its Claims write now uses the shared helper and roleVersion 1, while existing pending/error behavior remains.

## Custom Claims writers

## Risks and scope limits

- This phase does not add the scheduled reconciler. If no healthy Admin can call the current reconciliation callable, an interrupted transition can remain pending until B2 introduces service-identity recovery.
- Technician orphan cleanup and complete provisioning journal are deferred by B1 scope. The Auth-create/profile-failure rollback limitations remain.
- Last Admin protection still needs emulator tests invoking the production `beginRoleTransition` path for last-Admin demotion/deactivation and concurrent role changes. Existing local simulation tests are not sufficient evidence.
- Legacy version-1 acceptance is intentionally narrow but still means those profiles have no version claim until their first role transition. Monitor legacy profile distribution before considering removal of the compatibility branch.
- Seed requires built Functions output and an operator environment. Counter mismatch remains fail-closed; seed does not reconcile an existing invalid counter automatically.
- No Firebase deployment, production data access, seed execution, or service-account access occurred.
